Guia de migracion a MongoDB + vertical slices
=============================================

1) Arquitectura recomendada
---------------------------
- El frontend NO se conecta directo a MongoDB.
- Crear backend (Node + Express + Mongoose) con API REST.
- Frontend cambia de urlGoogle a API_BASE_URL (/api/...).
- localStorage puede quedar como cache temporal, pero MongoDB es la fuente de verdad.


2) Base de datos (colecciones recomendadas)
-------------------------------------------

[A] clientes
- Proposito: datos del cliente activo.
- Campos sugeridos:
  - _id (ObjectId)
  - nombre (String, requerido)
  - telefono (String)
  - placa (String, requerido, UNIQUE, uppercase)
  - categoria (String)
  - fechaActual (Date o String ISO)
  - fechaFutura (Date o String ISO)
  - km (Number o String)
  - activo (Boolean, default true)
  - createdAt, updatedAt
- Endpoints:
  - GET    /api/clientes
  - GET    /api/clientes/:id
  - POST   /api/clientes
  - PUT    /api/clientes/:id   (o PATCH)
  - DELETE /api/clientes/:id   (preferible borrado logico: activo=false)

[B] citas
- Proposito: agenda de reservas.
- Campos sugeridos:
  - _id (ObjectId)
  - clienteId (ObjectId | String)
  - placa, nombre, telefono, categoria (snapshot rapido)
  - fecha (Date o YYYY-MM-DD)
  - hora (String HH:mm)
  - espacio (enum: carcamo, gato_hidraulico, gato_electrico)
  - notas (String)
  - estado (reservada, cancelada, completada)
  - createdAt, updatedAt
- Endpoints:
  - GET    /api/citas
  - GET    /api/citas/:id
  - POST   /api/citas
  - PATCH  /api/citas/:id      (mover hora/fecha/espacio o editar notas)
  - DELETE /api/citas/:id

[C] historial_servicios
- Proposito: historial por placa (incluye registros eliminados o antiguos).
- Campos sugeridos:
  - _id
  - clienteId (opcional)
  - nombre, telefono, placa, categoria
  - fechaActual, fechaFutura, km
  - eliminado (Boolean)
  - fechaRegistro
  - createdAt, updatedAt
- Endpoints:
  - GET    /api/historial?placa=ABC123
  - GET    /api/historial/:id
  - POST   /api/historial
  - PATCH  /api/historial/:id
  - DELETE /api/historial/:id (solo admin, opcional)

[D] contactos_log
- Proposito: bitacora de clientes contactados.
- Campos sugeridos:
  - _id
  - clienteId
  - nombre, telefono, placa, categoria
  - fechaActual, fechaFutura, km
  - fechaContacto
  - canal (whatsapp, llamada, otro) opcional
  - resultado (respondio, no_respondio, pendiente) opcional
- Endpoints:
  - GET    /api/contactos-log
  - POST   /api/contactos-log
  - DELETE /api/contactos-log/:id

[E] usuarios
- Proposito: autenticacion real (reemplazar credenciales hardcodeadas).
- Campos sugeridos:
  - _id
  - usuario (UNIQUE)
  - passwordHash
  - rol (admin, taller, etc.)
  - activo
  - createdAt, updatedAt
- Endpoints:
  - POST   /api/auth/login
  - POST   /api/auth/logout
  - GET    /api/auth/me
  - POST   /api/usuarios        (admin)
  - PATCH  /api/usuarios/:id    (admin)


3) Indices clave en MongoDB
---------------------------
- clientes: unique index en placa.
- citas: unique index compuesto en (fecha, hora, espacio).
- historial_servicios: index en placa y fechaActual.
- contactos_log: index en fechaContacto.


4) Vertical slices (orden recomendado) + funciones frontend a modificar
-----------------------------------------------------------------------

SLICE 0: Infra base (config + capa API)
- Objetivo:
  - Preparar frontend para hablar con backend sin romper flujo.
- Archivos/frontend:
  - js/config.js
    - Reemplazar const urlGoogle por const API_BASE_URL.
  - (Recomendado) crear js/api.js con helpers:
    - apiGet, apiPost, apiPut/apiPatch, apiDelete.
  - index.html
    - Incluir js/api.js antes de modulos que lo usen.
- Nota:
  - Este slice no cambia logica de negocio, solo la infraestructura.

SLICE 1: Clientes
- Objetivo:
  - Migrar CRUD de clientes a /api/clientes.
- Funciones frontend a modificar:
  - js/clientes.js
    - submit de clienteForm (guardar cliente): cambiar POST a /api/clientes.
    - eliminarCliente(id): cambiar a DELETE /api/clientes/:id.
    - guardarEdicion(): cambiar a PUT/PATCH /api/clientes/:id.
  - js/sync.js
    - sincronizarConSheets() -> leer clientes desde GET /api/clientes (o /api/sync).
- Endpoints backend usados:
  - GET /api/clientes
  - POST /api/clientes
  - PUT/PATCH /api/clientes/:id
  - DELETE /api/clientes/:id

SLICE 2: Citas (Agenda)
- Objetivo:
  - Migrar reservas y reprogramaciones a /api/citas.
- Funciones frontend a modificar:
  - js/agenda.js
    - confirmarReserva(): POST /api/citas.
    - eliminarCita(citaId): DELETE /api/citas/:id.
    - onDrop(event, nuevaHora): PATCH /api/citas/:id.
  - js/sync.js
    - sincronizarSoloCitas() -> GET /api/citas (o /api/sync).
  - js/navigation.js
    - seleccionarTab(tab): actualizar llamada de sync para agenda.
    - setInterval(..., 30000): mover a sincronizacion nueva de citas.
- Endpoints backend usados:
  - GET /api/citas
  - POST /api/citas
  - PATCH /api/citas/:id
  - DELETE /api/citas/:id

SLICE 3: Historial
- Objetivo:
  - Hacer que el historial venga desde backend y no solo localStorage.
- Funciones frontend a modificar:
  - js/historial.js
    - buscarHistorial(): usar GET /api/historial?placa=...
  - js/clientes.js
    - en guardado/edicion/eliminacion, sincronizar snapshot de historial (si no es automatico en backend).
  - js/sync.js
    - incluir descarga/merge de historial si lo necesitas offline.
- Endpoints backend usados:
  - GET /api/historial?placa=
  - POST /api/historial (si aplica)
  - PATCH /api/historial/:id (si aplica)

SLICE 4: Contactados
- Objetivo:
  - Persistir bitacora de contacto en backend.
- Funciones frontend a modificar:
  - js/contactados.js
    - toggleContactado(id): POST /api/contactos-log al marcar.
    - mostrarContactados(filtro): GET /api/contactos-log.
    - eliminarLogContactado(id): DELETE /api/contactos-log/:id.
  - js/sync.js
    - incluir sync de contactos si mantienes cache local.
- Endpoints backend usados:
  - GET /api/contactos-log
  - POST /api/contactos-log
  - DELETE /api/contactos-log/:id

SLICE 5: Auth
- Objetivo:
  - Sacar usuarios hardcodeados y autenticar contra backend.
- Funciones frontend a modificar:
  - js/auth.js
    - intentarLogin(e): POST /api/auth/login en lugar de validar USUARIOS local.
    - verificarSesion(): validar token/sesion con GET /api/auth/me.
    - cerrarSesion(): POST /api/auth/logout (si usas sesion server-side).
  - js/config.js
    - remover arreglo USUARIOS cuando ya no se use.
- Endpoints backend usados:
  - POST /api/auth/login
  - GET /api/auth/me
  - POST /api/auth/logout


5) Recomendacion de estrategia
------------------------------
- Haz backend primero y luego migra frontend por vertical slices.
- No migres todo al tiempo: cada slice debe quedar funcionando de punta a punta antes del siguiente.
- Orden recomendado:
  1) Slice 0 (infra)
  2) Slice 1 (clientes)
  3) Slice 2 (citas)
  4) Slice 3 (historial)
  5) Slice 4 (contactados)
  6) Slice 5 (auth)


6) Contrato minimo inicial para arrancar rapido
-----------------------------------------------
- GET    /api/sync                  -> { clientes: [...], citas: [...] }
- GET    /api/clientes
- POST   /api/clientes
- PUT    /api/clientes/:id
- DELETE /api/clientes/:id
- GET    /api/citas
- POST   /api/citas
- PATCH  /api/citas/:id
- DELETE /api/citas/:id
